# 注册可用性与写入恢复设计

## 目标

恢复生产 SQLite 写入权限，并让学生在注册时就知道用户名是否可用，不必填写完整表单后才发现失败。

## 用户体验

注册页按以下优先级展示用户名状态：

1. 空输入：提示用户名格式规则，注册按钮不可用。
2. 格式不合规：红色显示格式错误，不请求服务器，注册按钮不可用。
3. 格式合规：停止输入 400ms 后查询可用性；查询期间显示“正在检查用户名…”，注册按钮不可用。
4. 用户名已存在：红色显示“该用户名已被使用，请换一个”，注册按钮不可用。
5. 用户名可用：绿色显示“用户名可用”。显示姓名和密码也合规时，注册按钮可用。
6. 检查异常：显示“暂时无法检查用户名，请稍后重试”，不把未知状态当作可用，注册按钮不可用。

提交注册仍由服务器以数据库查询和唯一约束最终裁决；若检查后发生并发抢注，409 响应仍显示“用户名已存在”。

## 后端边界

新增公开只读端点 `GET /api/v1/auth/username-availability?username=...`，返回 `{ "available": true | false }`。

- 沿用公开注册的用户名格式规则；不合规时返回 422 和明确规则文案。
- 每个来源 IP 在 5 分钟内最多 60 次检查，超限返回 429。
- 端点不创建账户，不记录推广归因，不改变登录与既有账号兼容性。

## 前端边界

在 `api.ts` 封装可用性请求；`LoginPage` 只管理输入、延迟查询、请求取消和状态展示。用户名变化、切换登录/注册模式或组件卸载时取消过期请求，旧响应不能覆盖新输入状态。

密码、显示姓名和用户名格式继续本地即时校验。提交按钮只在所有必填字段、可用性检查和本地规则均通过时启用。

## 生产恢复

SQLite 不仅需要数据库文件可写，也需要其父目录可创建 journal/WAL 文件。生产 `data/` 目录和数据库文件都由 `mathmind` 服务运行用户 `ubuntu` 持有并可写。修复权限后重启服务，并通过一次不创建账户的写权限检查和真实注册流程验证。

## 验收

- 服务端测试覆盖：可用、已占用、格式错误、限流。
- 前端测试覆盖：状态优先级及可提交判定。
- 浏览器验证格式错误、检查中、已占用、可用四种状态。
- 正式站健康接口正常；注册可创建账户并可随后登录。
